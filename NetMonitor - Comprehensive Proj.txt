# 📋 NetMonitor - Comprehensive Project Analysis Report

## 🎯 Project Overview

| Field | Details |
|---|---|
| Project Name | NetMonitor |
| Type | Full-stack defensive network monitoring and security analytics platform |
| Concept | Browser-based network command center for packet inspection, safe scanning, topology visualization, and explainable threat detection |
| Purpose | Monitor traffic, discover hosts, detect suspicious activity, visualize topology, and present security findings in a beginner-friendly and SOC-grade UI |
| Architecture | Event-driven full-stack system with FastAPI backend, React/Vite frontend, async services, WebSocket fanout, and SQLite persistence |
| Languages | Python, TypeScript, HTML, CSS, JSON, shell/batch scripts |
| Runtime | Python 3.9+ backend runtime; Node.js 18+ frontend tooling/runtime; FastAPI/Uvicorn service layer |
| Current Status | Actively developed, feature-rich, operationally oriented defensive monitoring platform with development defaults, local SQLite storage, and several production-hardening features already in place |

### Executive Snapshot

NetMonitor is not a generic dashboard. It is a deliberately safety-constrained defensive network intelligence platform with three dominant concerns:

1. Real-time observability of packet flow, host discovery, alerts, and topology state.
2. Conservative guardrails around scanning, capture, and alert generation.
3. A dual-mode user experience that supports both beginners and experienced operators.

The backend behaves like a telemetry and orchestration core. The frontend behaves like a SOC cockpit. The result is a system that emphasizes explainability, continuity, and defensive controls over raw feature density.

### Structural Notes

- The backend is organized as a service-oriented FastAPI application with cohesive domain modules rather than a monolith of route handlers.
- The frontend is organized around a route shell plus page-level workflows and reusable status widgets.
- The repository contains a checked-in virtual environment under backend/venv. It should be treated as an operational artifact, not as product source.
- The database file backend/netmonitor.db indicates local persistence is part of the development loop and likely used as the default runtime store.

## 🎨 Frontend / UI Analysis

### UI Structure

The frontend is a single-page application with a protected shell and nested route pages. The layout is intentionally modeled after a security operations center rather than a consumer app. It favors dense information, strong hierarchy, and immediate operational clarity.

| UI Layer | Description |
|---|---|
| Application shell | Persistent sidebar, mode switch, user panel, legal acknowledgment, and keyboard shortcut support |
| Overview dashboard | High-level posture summary with score, counts, protocol distribution, and recent alerts |
| Packet explorer | Live capture console with protocol-aware filtering and privacy-first packet display |
| Network scanner | Guided scanning workflow with safety cues, target validation, and aggressive-scan confirmation |
| Alert center | Evidence-first triage interface with search, filtering, acknowledgement, and detail expansion |
| Network map | Animated topology canvas with flow emphasis, selection, and live update integration |
| Settings | Profile, password, and detection rule management in a tabbed admin-style layout |

### UX Flow

1. User lands on the login screen and authenticates.
2. The auth token is persisted and rehydrated on refresh.
3. The legal consent banner blocks first-run usage until acknowledged.
4. The user enters the SOC-style shell and chooses a page.
5. Live telemetry begins to flow through REST polling and WebSocket channels.
6. The user can shift from beginner mode to expert mode for shortcuts and denser controls.
7. Operational tasks branch into capture, scan, alert triage, or topology analysis.

## 🔐 Backend / Runtime Architecture

### Execution Flow

```text
User Login
   ↓
JWT Issuance
   ↓
Protected Route Shell
   ↓
Dashboard / Capture / Scan / Alerts / Topology
   ↓
REST API and WebSocket Transport
   ↓
Service Layer (Capture, Detection, Alerting, Topology, Scanner)
   ↓
SQLite / Runtime State / Metrics / Audit Trail
```

### Lifecycle Flow

```text
FastAPI Startup
   ↓
Create database tables
   ↓
Instantiate alert, detection, topology, capture, websocket, and monitor services
   ↓
Register callbacks between services
   ↓
Start background monitors and retention workers
   ↓
Resolve gateway and populate app state
   ↓
Serve REST + WebSocket traffic
   ↓
Shutdown cleanup and stop background services
```

### Event and Async Model

The backend uses event-driven callbacks heavily. Packet capture, detection, topology updates, ARP monitoring, and interface changes all emit structured events that are fanned out to the WebSocket manager or consumed by other services. This keeps the live UI synchronized without forcing the frontend to infer state from polling alone.

### State Management

| State Domain | Where It Lives | Notes |
|---|---|---|
| Authentication | Frontend localStorage + backend JWT | Rehydrated on startup, attached through Axios interceptors |
| Capture runtime state | Backend app state + capture service object | Shared across API routes, metrics, and WebSocket broadcasts |
| Detection and alert state | Detection engine + alert manager | In-memory operational state with DB support for related records |
| Topology graph state | Topology service | Maintains nodes, edges, activity, and change events |
| UI preferences | Zustand persistent store | Beginner/expert mode, sidebar state, packet display preferences, and notification toggles |

### Memory and Streaming Path

```text
Packet Sniffing
   ↓
PacketInfo Parsing
   ↓
Circular Buffer + Metrics Update
   ↓
Detection Engine Analysis
   ↓
Alert Manager / Correlation Engine
   ↓
Topology Service Update
   ↓
WebSocket Broadcast
   ↓
Frontend State Merge
```

### Routing and Orchestration

- REST routes are grouped by concern: auth, packets, scanner, alerts, dashboard, network, topology, health, and export.
- WebSocket channels separate packets, alerts, stats, topology, and scans to reduce coupling.
- The app state acts as a service registry so route handlers can reach the active runtime services safely.
- The architecture is intentionally modular enough that background monitors and retention tasks can run independently of request traffic.

### Networking and Capture

The packet capture pipeline is metadata-first. It does not treat raw payload as the default experience; instead, it prioritizes source/destination metadata, protocols, ports, flags, and summaries. This is consistent with the defensive and privacy-aware intent of the product.

### Diagram: UI to Runtime Broadcast Path

```text

   ↓

```

|---|---|

## 🧠 Project Identity

### Design Philosophy

NetMonitor is built around disciplined defensive visibility. It prefers semantic clarity, bounded behavior, and explicit consent over raw operational freedom. This is reflected in the legal banner, local-only defaults, conservative scan profiles, and explainable alerting.

### System Identity

This is a security operations cockpit for small-to-medium defensive use cases: home labs, SOC training, internal network monitoring, and authorized security audits. It is intentionally shaped to be both educational and operational.

### Architecture Style

| Style | Characteristics |
|---|---|
| Event-driven | Packet, alert, topology, and monitor events propagate through callbacks and WebSockets |
| Service-oriented | Capture, detection, alerting, scanning, and topology are modular services |
| SPA + API | React frontend consumes a FastAPI backend via REST and WebSocket channels |
| Safety-constrained | Validation and rate limits are built into the domain logic |
| Explainability-first | Alerts and UI elements explain what was detected and why |

### Intended Use Case

- Defensive network monitoring.
- Security awareness and education.
- Internal troubleshooting and visibility.
- Authorized host discovery and service inspection.
- Network topology analysis and alert triage.

### Innovation Aspects

- Beginner and expert modes in the same operator UX.
- Evidence-first alert presentation rather than alarm-only display.
- Real-time topology with activity levels and edge bandwidth cues.
- Defensive guardrails embedded directly into scanning and capture flows.
- Semantic design tokens that encode risk, protocol, and status meaning.

## 📌 Strengths & Improvements

### Strengths

- Strong separation between transport, service logic, and presentation layers.
- Live telemetry pipeline is thoughtfully connected from packet capture to WebSocket client.
- Safety controls are not superficial; they are implemented in validators and service logic.
- The UI is coherent, polished, and purpose-built for operations work.
- The project already includes comprehensive documentation and architecture notes.

### Bottlenecks

- Some state is kept in memory, which limits horizontal scaling without an external store.
- Scapy and Nmap dependencies tie core features to host-level system support.
- The checked-in virtual environment suggests repository hygiene could be improved.
- Several views rely on repeated polling fallback paths in addition to WebSockets.
- SQLite is appropriate for local and light deployments, but not ideal for high-concurrency production.

### Scalability Notes

| Area | Constraint | Implication |
|---|---|---|
| Packet buffer | Bounded in-memory deque | Good for safety, limited for high-throughput retention |
| Alert storage | In-memory alert manager plus local DB | Needs external persistence for clustered deployments |
| Topology state | In-memory graph | Would benefit from a shared cache or persistence layer in multi-node setups |
| WebSocket fanout | Single-process manager | Needs distribution strategy for horizontal scale |
| SQLite backend | Local file-based database | Suitable for development and small deployments, not for distributed writes |

### Optimization Opportunities

- Move runtime state that must survive restarts into a proper persistence or cache layer.
- Introduce stronger schema-sharing between backend API models and frontend TypeScript interfaces.
- Add more uniform response-shape normalization to reduce client-side defensive parsing.
- Reduce the presence of checked-in artifacts and generated files.
- Consider using a shared event bus if the system grows beyond a single-process deployment.

### Future Improvements

- Add a more explicit role-based permissions layer in the UI and backend.
- Expand export formats and scheduled reporting.
- Add cross-session alert correlation and searchable timelines.
- Introduce deployment profiles for containerized or service-managed operation.
- Add formal test coverage for the real-time event flows and safety validations.

## 🎮 User Interaction Flow

### Full Journey

1. The user opens the application and is presented with the legal consent banner if consent has not yet been stored.
2. After acceptance, the user reaches the login page and submits credentials.
3. The backend issues a JWT and the frontend stores it persistently.
4. The sidebar shell loads with navigation, expert/beginner mode controls, and user identity.
5. The dashboard begins fetching summary statistics and shows live posture information.
6. The packet explorer opens, selects a capture interface, and either streams packets live or polls as fallback.
7. The network scanner validates a target, enforces safety rules, and starts a constrained scan when allowed.
8. Alerts accumulate in real time; the user can filter, expand evidence, acknowledge, or clear them.
9. The topology map renders passive host and connection state, animating relationships in the graph.
10. Settings allow the user to change their password and toggle detection rules.
11. The user can export packets, alerts, or topology snapshots for analysis or reporting.
12. On shutdown or navigation away, the backend stops background services cleanly and preserves the configured state.

### Interaction Style Observations

- The app is designed to be usable by beginners without hiding the technical details from advanced users.
- The UI makes risk visible instead of abstracting it away.
- Operational actions are usually paired with confirmations, safety labels, or explanatory copy.

## ✅ FINAL SUMMARY

NetMonitor is a substantial defensive network monitoring platform with a clear and coherent identity. It combines packet capture, safe scanning, alerting, topology visualization, and operational telemetry into a single browser-based security console. The backend is organized as a modular, event-driven FastAPI system with strong safety and observability patterns. The frontend complements that backend with a polished SOC-style shell, live widgets, guided workflows, and a meaningful beginner/expert dual-mode experience.

The project’s strongest characteristics are its explainability, its defensive posture, and its real-time architecture. The most important limitations are the reliance on local in-memory state for some runtime data, the development-oriented SQLite default, and the presence of checked-in environment artifacts. Even with those caveats, the codebase already reads like a serious technical product rather than a prototype. It is structured, documented, and intentionally designed around safe operational use.

From an architectural perspective, NetMonitor is best described as a real-time, safety-constrained, event-driven network defense cockpit built with FastAPI, React, WebSockets, Scapy, and SQLite. Its current shape is strong enough for local and small-team defensive use, and it has a clear path toward more durable persistence and distributed runtime support if the project grows.
